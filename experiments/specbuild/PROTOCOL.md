# Specification construction from an independently authored regulation: protocol

Written 2026-10-11, before any creation, validation, or test step was run.
Goal: evaluate a realistic, protocolized workflow in which an LLM turns
independently authored requirements into a PRIME program, with program
creation, validation, and testing separated by data, and report end-to-end
authorization error and coverage against an independent reference.

## Requirements, records, and reference

- **Requirements:** 42 CFR Part 11 (FDAAA 801), written by Congress, FDA and NLM. The creator receives the text of the definitions in 11.10 that the operative sections use, 11.22(b), 11.42, and 11.44(a) to (c), fetched from the eCFR API on 2026-10-11 (`inputs/cfr_42_*.txt`).
- **Records:** ClinicalTrials.gov API v2 registrations.
- **Reference:** the FDAAA TrialsTracker export of 3 August 2026, an independently written decision procedure over the same registry. Reference level of a registration: 3 when the tracker status is reported-late; otherwise 2 when the tracker marks results due (reported on time, overdue, overdue-cancelled); otherwise 1 (not yet due). Every tracker trial counts as applicable, so level 0 never occurs. The reference is an external classification, not legal adjudication; its conventions (for example a 30-day administrative grace) are part of what is measured.

## The review program the creator must produce

The review questions are fixed (they are the owner's request): C1 the registration is an applicable clinical trial subject to the results-reporting requirement; C2 results information was due by a determinate date that has passed by the snapshot date (3 August 2026); C3 results information was submitted after that deadline. The creator writes the rest: atoms, each a predicate from the runtime's closed ten-predicate grammar on one field of the embedded record or on one derived field; an optional `derive(study)` Python function that computes derived fields from the record (run in a sandbox with restricted builtins and a time limit); and the sufficient routes for C1 to C3. It sees no tracker label and no test record.

## Phases

1. **Creation (round 0).** Creator: Qwen2.5-32B-Instruct, the paper's primary model, served locally with vLLM. Inputs: the regulation text, a field catalog of the embedded record (paths, types, enumerated values observed in development-pool records, short descriptions from the ClinicalTrials.gov data dictionary), three unlabelled example records from the development pool that are not in the validation sample, and the program format. One greedy and eight sampled candidates (temperature 0.7, seeds 1 to 8).
2. **Validation.** Validation set: 600 registrations drawn uniformly (seed 20261011) from development-pool registrations listed in the tracker export, re-fetched in full from the public API on 2026-10-11, like the test records. A candidate is valid when it parses, its `derive` compiles in the sandbox, and its instances pass the runtime's schema validation (order coherence, non-domination, registered resolvers). Amended before any run: a record on which `derive` raises gets no derived values, so atoms that read them stay unresolved (fail-closed); the error count is reported and fed to the repair round. If no round-0 candidate is valid, program B does not exist and only program A is tested. Score: agreement between the program's full-evidence level (the strongest conclusion its routes license when every atom is resolved) and the reference level. Selection rule: highest agreement; ties broken by fewer over-claims (program level above the reference), then by fewer atoms.
3. **Repair (one round).** The selected round-0 program and up to 12 validation disagreements (the record's relevant fields, the tracker status, and the program's level) go back to the creator for one greedy and eight sampled revisions. Final selection over all valid candidates of both rounds by the same rule. The selected program is frozen and hashed before the test phase.
4. **Test.** Test set: the 1,999 held-out registrations fetched on 2026-10-10 for the paper's held-out evaluation, drawn from sponsors absent from the development pool. Two programs: (A) the paper's program, built earlier by the coding assistant with readings selected against the tracker on the development pool, run through its unchanged builder (whose exclusions are abstentions); (B) the frozen program of phase 3. For each program, PRIME instances are built for every test registration the program can process, and four policies run: the fully informed agent (unenforced), PRIME without completion, PRIME with completion (Qwen2.5-32B-Instruct, greedy, 20 calls), and the ceiling-targeting policy with no LLM. The LLM policies run on a uniform random subset of 600 test registrations drawn by id (seed 20261011) before any label is read; the ceiling-targeting policy covers all 1,999. Records are shipped to the cluster reduced to the modules the two programs read (`reduce_records.py` verifies that the reduction leaves every embedded record and every instance of program A unchanged). Tracker labels for the test set are read only by the final scoring step, after all episodes.

## Reported

Over all 1,999 test registrations: unsupported-conclusion rate (stated level above the reference level), supported utility (33.3, 66.7, 100 for the strongest stated conclusion at or below the reference level, 0 otherwise), coverage (any conclusion stated), abstention, the paper's adverse-against-adverse classification agreement, and the same by tracker status; validation scores of every candidate; the frozen program; and the cost of each phase.

## Deviation log

- **Run 1 discarded (job 13948248, 2026-10-10 23:06–23:20).** The sandbox's import filter rejected `_strptime`, the internal module `datetime.strptime` loads on first use, so every candidate that parsed dates failed on most or all records; the selected program reached 0.2% validation agreement for that reason alone. The run was cancelled after building test instances, before any agent episode or test label. Three harness fixes, made from the format errors in that run's candidates and not from any agreement score: (1) the sandbox returns the already-imported `_strptime` and allows `calendar`; (2) the field catalog writes list items as `path.N` (a 0-based index the runtime resolves) where it had written `path[]`, which the runtime cannot resolve and one candidate copied; (3) the format text states that a predicate's argument is a constant and that comparisons between fields belong in `derive`, after two candidates passed a field name as an argument. The whole workflow was then rerun from creation with the same model, seeds, inputs, and splits.
- **Run 2 discarded (job 13948550, 2026-10-10 23:26–23:42).** `datetime.strftime` loads the `time` module through the sandbox's import hook, and some candidates import `time` directly; the filter rejected it, so derive failed on most records and every program scored level 0 on the validation set. Cancelled during the first agent arm, before any test label. Fix: `time` is allowed (it gives no file, process, or network access). Every candidate of run 2 was then re-evaluated locally with the fix: levels became non-degenerate (validation agreement 31% to 47% for the first candidates), and the remaining derive errors are the candidates' own (for example `strptime` with a day format on month-precision dates), which fail closed per record as specified. The workflow was rerun from creation a third time, unchanged otherwise.
